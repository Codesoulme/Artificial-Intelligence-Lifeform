# DeepSeek 聊天进程的在线状态

聊天入口可通过 `--awake-state` 加载训练过的 P24 模块。模块作为孢子个体的 CPU 子模块运行，在等待输入和生成回答期间按已有模式频率更新。它保存运行张量和计数，状态文件绑定模型来源与记忆文件路径。在线状态每五秒及退出时原子保存。

```powershell
cd D:/SPORA
.venv/Scripts/python.exe scripts/deepseek_continuous_memory_chat.py --awake-state 'runs/awake-chat.pt'
```

输入 `/status` 查看状态，`/relax` 放松，`/focus` 专注，`/sleep` 暂停在线模块的更新，`/wake` 恢复。此入口沿用本地的 P24 seed 7 检查点及 DeepSeek 聊天产物。

真实聊天进程的两个约 1.1 秒无输入窗口中，放松模式推进 5 次神经更新，专注模式推进 18 次。睡眠窗口推进 0 次，并累计约 1.1 秒睡眠时间。唤醒后，聊天进程从 SQLite 记忆读出了“香橙冰茶”。退出前最后一次状态查询显示 27 次更新，新进程首次状态查询显示 29 次。重新加载期间累计约 43.8 秒的离线间隔，未补算神经更新。两次进程的外部观察计数均为 0。已有在线模块及时间测试共 18 项通过。

初版在线循环和语言生成由同一线程推进。一次约 3 秒的生成超过了已有的两秒更新间隔上限，被记入间隔。重启沿用 P24 的失效规则，累计时间和计数会保留，依赖连续观察的工作向量会重置。

## 生成期间持续更新

改用独立 CPU 调度线程，状态查询、模式切换和保存共用同一把锁。实机生成“这个人最喜欢的饮品是香橙冰茶”耗时约 3.31 秒，在线模块推进 13 次，运行间隔计数保持为 0。各约 1.1 秒的放松、专注和睡眠窗口分别推进 4、19 和 0 次更新。退出后核验了在线状态和 SQLite 摘要。19 项测试通过，新增用例验证聊天迭代器交出一条输入后，递推和定期保存仍会继续。

首次实机测试在在线模块启动前遇到 Transformers 向 GPU 直接映射权重时的 Windows 访问冲突。聊天入口改为 Windows 上先加载到 CPU，再转到 GPU，重跑通过。尚未测量长期运行时的资源开销或原生崩溃频率。在线递推仍使用有限图任务训练得到的模块，聊天语义与睡眠巩固尚未接入。

## 从聊天接收主题信号

启用 `--awake-state` 后，模型把字段分类器从 DeepSeek 隐藏状态算出的概率分布交给 CPU 主题模块。模块在在线更新中用固定的时间常数积累并衰减激活。`/status` 的 `topics` 字段显示各主题激活和输入计数。睡眠时暂停接收输入和推进激活，重启或出现运行间隔时清除短时激活，已保存的输入计数可以恢复。

对照给同一递推分别输入饮品和职业概率，得到不同的最高激活。无输入对照保持为零。实机问何程最爱喝什么，饮品激活达到 0.45，等待 2.2 秒后降至 0.15。随后询问齐宁的职业，职业激活升至 0.64。睡眠 1.1 秒内主题状态保持一致。两个问题都读出正确的既有记忆，退出时保存了两次主题输入，SQLite 记忆摘要保持一致。在线模块的九项测试通过。

主题模块目前只接收字段概率并通过状态命令读出。激活系数由实验设定，尚未用于控制语言生成、记忆选择或睡眠巩固。

## 主题状态对追问路由的影响

复用五组共 70 条留出对话和同一组字段分类器。用当前问题的隐状态判断是否承接前文。近期主题由前一条消息的字段分数驱动，按 250 毫秒步长推进到 1 秒。过期对照推进到 10 秒。置换对照循环移动主题向量的字段位置，保留各激活值和总量，用于模拟错误的近期主题。

保留前文时，只在已判定承接且原字段置信度低于放行阈值的样本上，按固定权重 0.4 混合近期主题分布。近期、置换和过期三组都没有改变最终字段或放行动作。移除前文的对照则让已经判定承接的追问只使用达到活跃度和置信度门槛的主题，未达到门槛时请求澄清。

| 路由输入 | 字段正确 | 正确放行 | 错误放行 |
|---|---:|---:|---:|
| 保留上一轮原文 | 65/70 | 34 | 0 |
| 只看当前问题 | 27/70 | 13 | 0 |
| 当前问题与近期主题 | 60/70 | 29 | 0 |
| 当前问题与置换主题 | 25/70 | 13 | 10 |
| 当前问题与过期主题 | 27/70 | 13 | 0 |

近期主题保留了部分追问所需的字段信息，错误状态也可能导致错读。实验只计算字段和读取放行，未运行端到端回答或验证人物绑定。参数固定，样本来自已有的手写留出题。聊天入口继续使用原路由。复现脚本为 `scripts/deepseek_awake_topic_recall.py`，完整的八组结果位于 `runs/deepseek-awake-topic-recall-context-ablation/`。

## 单轮追问的端到端读取

实验入口增加 `--awake-topic-recall`。上一轮须明确点名，生成的事实部分须与记忆矩阵的逐位置最高分词元一致，并以结束符收尾，才会保留人物地址与字段供下一轮使用。下一轮不传入上一轮的文本。它需要命中现有省略句规则、通过承接判定，并且在线主题激活仍支持该字段。通过一次追问后，读取结果不会重新绑定人物。睡眠会清除这个实验使用的短时主题。

首次实机测试选中了沈亦和饮品字段，但沿用普通回答的开场等待，最终未开始注入记忆。改用同一词元偏置处理器从首个生成位置开始解码，最多生成八个词元。生成序列须再次与矩阵核对到结束符，否则请求澄清。

```powershell
cd D:/SPORA
.venv/Scripts/python.exe scripts/deepseek_continuous_memory_chat.py --awake-state runs/awake-topic-recall.pt --awake-topic-recall --memory-file runs/deepseek-continuous-memory-capacity-batched/timeline-smoke.sqlite3 --inherited-router --retrained-gate --earlier-readout --json
```

| 首轮问题 | 紧接着问「查到了就说一下。」 |
|---|---|
| 沈亦平常最爱喝什么？ | 香橙冰茶 |
| 这次要填履历，齐宁当时做的是哪份工作？ | 织机检修师 |
| 齐宁那次去了哪里？ | 新荷档案馆 |

在同一个实机进程中，改问温谨读出了桂花乌龙。追问用过一次、查询空字段、等待 4.5 秒、进入睡眠或随后唤醒的对照都请求明确查询对象，SQLite 文件的 SHA-256 保持一致。现有姓名规则无法解析「那次经历中，沈亦去过哪个地方？」，即使字段路由正确也会请求澄清。换成「沈亦那次去了哪里？」可以识别人名，检查点中该字段为空。在线模块、观察解析和记忆输出的 21 项单元测试通过。

事实来自持久化神经记忆矩阵，短时字段偏好来自在线张量。人物地址仍由聊天进程暂存到下一轮。这批样本仅验证三个字段和固定的追问措辞，开放式共指、跨多轮延续和把人物绑定纳入模型状态仍待验证。

## 人物绑定迁入在线模块

在线主题模块用运行时张量存放人物地址和字段索引。命名读取通过事实核对后写入。每个后续问题在调度锁内消费一次绑定，主题已经衰减或字段不匹配时立即丢弃。睡眠和运行间隙清除绑定。绑定随进程结束失效，旧版在线状态文件可按原格式恢复。

实机重新跑通三类追问、显式换人、缺失记录、等待 4.5 秒和睡眠后立即唤醒。最后一轮重新点名查询，确认已经绑定，再退出并加载同一份状态文件。新进程里的省略追问请求明确查询对象。SQLite 摘要通过核验，相关的 23 项单元测试通过。

对现有承接分类器做了措辞探测。阈值为 0.75，「能再说一遍吗？」等八条新复述请求均通过分类器，均未通过现有句式规则。「这个我知道了」「不查了，谢谢」「换个人看看」「前一版记的是什么」「还可以查哪些内容」也通过分类器。其余三条对照涉及时间、饮品推荐和资料整理，分数均未过阈值。这表明承接分类器还需要学习区分复述、取消与改问，才能扩大可用句式。
