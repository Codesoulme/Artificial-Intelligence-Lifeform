# P114 基准后的真实候选试点与扩展方案

## 决策与当前状态

方案制定时要求先完成受保护的万条合成基准，再对已完成、身份已核对的 P112 候选文件做串行小试。此后 P112 筛选与万条合成基准均已结束，结果见 `P112-controlled-screen-result.md` 和 `P114-disk-dedupe.md`。小样本的成功只能证明该样本上的资源和行为，不能推断 20 万行必然完成，也不能证明语义隔离。

本方案不读取开发集或最终测试正文，不运行 P112、不修改其文件或检查点。唯一真实正文输入是 P112 **完成后**生成的候选 `candidates.jsonl`；确认其成功摘要、输入输出摘要和文件大小稳定，且筛选进程及其他重负载作业均结束。来源是否合规由运行者核实；不打开尚在写入的文件。所有副本、SQLite 和结果含原文，仅存于忽略提交的 `runs` 子目录，不提交。

## 对现有代码的资源审查

设 N 为记录数，L 为典型文本长度，G 为单条不同五元组数，P 为去重后的候选对数，B 为某个桶的成员数，C 为受理桶中 `B(B-1)/2` 之和。以下是算法上界和代码结构，非运行实测：

| 阶段 | 时间及磁盘行为 | 影响 |
|---|---|---|
| 导入、摘要、分桶 | 文本规范化和集合生成与文本长度相关，32 项签名约 32G 次 Python 哈希变换；每条最多插入 8 个桶条目，另有主记录及两个索引的 B 树操作 | CPU 随总字数变化；96 字的合成基准不能代表更长的真实故事。数据库保存 JSON 原行和文本两份，输出还可能再次保存原行 |
| 候选生成 | 扫描桶索引；受理桶枚举 C 次组合、插入去重表，P ≤ C ≤ `max_pairs`；单桶内存 O(B)，上限为 `max_bucket` | 默认 200 条的桶可能枚举 19,900 对；同一对重复出现仍重复消耗预算，且字典序决定哪些桶被跳过 |
| 核验 | P 次从磁盘取两条文本，重新构建完整集合并计算交并；约 O(各候选对的文本长度之和)，另含数据库访问与并查查询 | 同一长故事参与多对时反复分词和读取；P 达到 100 万时可能是主耗时，磁盘/CPU 耗时不由 N 单独决定 |
| 连通分量 | 每次查根逐个 SELECT 父节点，按最小根连接；查根时迭代压缩路径，输出阶段每行另查原因 | 初次遇到深链仍需遍历和更新，后续查询通常更短；没有按秩平衡，不能保证所有操作均为常数时间 |
| 内存与磁盘 | 不保存全量特征在内存；单行受字节数上限约束，但解码、规范化和 Python 集合膨胀，峰值随两条文本及特征数变化；SQLite 缓存按配置，系统页缓存另计 | `max_line_bytes`、`max_bucket`、缓存及进程提交阈值都需控制；数据库、回滚日志、输出、临时排序文件和磁盘剩余需分别考虑 |

低负载合成核查：内存 SQLite 中构造 300 节点递减父链，按升序查询全部节点。原方法执行 45,150 次父节点 SELECT、0 次 UPDATE，用时 0.239 秒；迭代压缩执行 1,493 次 SELECT、298 次 UPDATE，用时 0.013 秒。两次在同一测试进程测量，均返回第 1 行；时间仅为一次样本，含 SQL 跟踪开销，不能外推到磁盘、真实数据或全量耗时。压缩采用两次迭代，不保存整条链；父节点更新属于调用者事务，回滚可撤销，不改变按较小根合并的规则。合成测试还比较了修改前后输出及风险传播，并覆盖事务回滚。单次深链遍历仍耗费 O(链长) 数据库操作，写入也带来日志与磁盘成本；路径压缩不是硬资源或运行时间上限。

目前桶级 `INSERT ... SELECT`、成对插入、组风险汇总以及单条签名/大文本处理期间不会调用资源检查；资源阈值为采样保护，不是硬上限。SQLite 的临时文件可能位于输出目录以外，目录大小采样不包括它们；提交前回滚日志也可能增长。当前进程保护只检查提交量和可用物理内存，不检查系统可用提交量、剩余运行时间、其他作业或峰值工作集；应由外层低优先级监督器每 0.25–0.5 秒检查，超限仅终止自己启动的试点子进程。外部终止可能无法写 `failure.json`，缺少成功摘要及独立核对即判失败。监督器与 SQLite 页数上限都不能构成硬磁盘配额。

代码读取源时计算摘要，但不锁定输入或在开始/结束各自计算完整摘要；若源被并发改写，成功摘要只是实际读到的字节流摘要。试点必须在筛选完成后把输入完整散列，与 P112 的成功摘要核对，采样结束后再次散列并比较，且检查文件身份、大小及修改时间；这不能从逻辑上防止蓄意并发写入，运行期应确保源文件由使用者保持不变。非正常退出或不一致时废弃本次输出。

## 合成基准的准入门槛

待相关作业均结束、机器空闲且系统可用内存达到保护线，再串行运行 `scripts/p114_synthetic_benchmark.py` 的 10,000 条配置，禁止与试点重叠。最低配置按 P114 报告：子进程提交量上限 192 MiB、系统可用物理内存下限 1,536 MiB、数据库/输出采样上限 512 MiB，0.25 秒监督；机器条件不足就不启动。阈值为建议起点，不保证消除瞬时超限。检查运行器是否覆盖全部实际重负载进程，名字匹配不能替代人工确认。

记录子进程峰值工作集、峰值提交、最低系统可用内存、目录峰值、空闲磁盘、总耗时、退出码、构造对同组率、隔离率、候选对及未检桶数量；核对摘要和组覆盖。基准包含短随机文本和一类固定改动，无法模拟真实文本长度、常见开头、桶偏斜或语义差异。若触发保护、输出不完整或已知测试对存在异常，先排查，不进入真实试点；构造对未召回需记录，不应直接解释为实现错误或真实召回率。

## 小规模真实候选试点

1. 仅对已完成的候选文件做两次流式完整摘要校验，并在新 `runs` 目录保存来源摘要、字节数、行数、脚本摘要、参数、时间与过程记录，不记录正文到报告。采样应按固定种子与稳定身份（例如 `SHA256(seed || source_row_1based || sha256)`）决定，从全文件均匀抽取最多 500 条；按原文件行号排序写入新目录，保存源行号映射。使用大小为 500 的有界堆或两阶段磁盘排序，不依赖 Python 全量列表。来源记录若缺少唯一行号则以候选文件行号为准，重复身份用行号区分。
2. 先单进程跑 500 条；正常退出后才评估最多 2,000 条的第二个独立样本。第二次采用相同规则和同一固定种子使 500 条为 2,000 条的子集，方便对照；组关系变化正常，因为新增记录可能形成桥接。不要把两个样本作为分片结果拼成全局结论。条数不足时记录实际数量。所有试点输出均是研究样本，不投入训练。
3. 两次均用 `--max-memory-mib 192 --min-available-mib 1536 --max-disk-mib 512 --max-bucket 200 --max-pairs 1000000 --cache-mib 16` 作为初始上限，并由外部监督器记录工作集、提交量、系统可用物理内存和可用提交量、时间、输出目录及临时盘空闲空间。若 512 MiB 不足，停止评估，不自动上调；剩余磁盘应至少覆盖预算、SQLite 临时/回滚空间及额外余量。设置运行时间上限，初次建议 15 分钟，监督器只能结束自身子进程。保护被触发、系统内存不足或出现其他重负载时不启动下一阶段。
4. 逐行核对输入行各有唯一组条目，组代表为组中最小行号；候选输出等于无已知风险组的代表，隔离输出覆盖所有有风险的组成员；未检桶成员对应的整个组均隔离。验证输出摘要与摘要文件、输入两次摘要均一致，汇总特征短缺、超桶、预算三类原因的记录及组数、候选对数量、桶大小分位数、实际比较数、组大小分位数和耗时。P114 当前不单独输出上述所有聚合指标，可对 `index.sqlite3` 作只读聚合；避免在仍在运行的数据库上查询，控制 SQLite 临时排序和时间。人工抽样检查仅在获准的候选中进行，报告只记录行号及判断，不复制正文。
5. 对 500 条样本可做独立逐对完整五元组 Jaccard 参考（124,750 对），分块、限时、低内存且与其他作业串行，统计阈值以上对与 P114 **已验证候选对**的交集、差集及是否隔离；不能只看是否同组，因为传递闭包会掩盖漏检。记录分母、置信区间或实际数量：若正例极少，则召回估计无信息。对已抽取阈值以上对、边界附近对及 LSH 未检对做人工审阅，标注语义重复/不同，明确抽样方式及其选择偏差；不能把纯字面真值当语义真值。

全对参考需要读取样本候选正文，不读取任何留出正文；这个步骤可能比主试点更慢，必须同样受监督。试点无论效果如何均不证明跨数据集安全、真实语义召回或全局覆盖。

## 全局扩展设计

不应分别对每个分片独立去重后只合并代表：不同分片的非代表故事可能构成跨片桥接，未检桶和传递关系也会丢失。建议保持一个全局行号空间和全局边集合，分批仅是执行/存储方式：

1. 在完整且不可变的候选快照上，流式写入全局精确摘要及规范化前缀索引；摘要碰撞要核对全文，同前缀的不同原文保留参与签名。顺序和格式由版本化参数固定。
2. 把每条记录的全部签名桶条目写入全局外存索引，按 `(band, signature)` 外部排序或持久 B 树归并，不按文件分片截断桶。桶可按键范围切任务；同一桶完整落在一个任务里。确定性地生成并外部去重全局候选对，比较预算和跳过原因有可复核的全局账本。过大桶或预算不足仍须隔离其全部成员所属最终组；尝试对大桶分块全对比较时，必须覆盖全部块对，不能只比较块内。
3. 逐对从全局文本存储读取并验证完整五元组集合；对热点文本可用严格字节上限的有界临时集合缓存，缓存淘汰不能改变结果，或用磁盘排序/合并求交集。短文本、异常和失败均按既定规则标记。需要时以可恢复的任务表记录已完成范围及脚本/输入/参数摘要；重试必须幂等，任何部分任务不可当作完整结果。
4. 使用磁盘上的连通分量算法，支持路径压缩或基于大小的合并，同时独立维护最小输入行代表；全局合并后传播所有风险，最终一次输出。为外存排序、SQLite 日志、索引和结果预留实测放大系数及空间余量。阶段断点须带版本化清单、事务边界、校验和和完成标志；现有 P114 无恢复机制，不能在失败目录续跑。
5. 在多个合成分布上验证：跨任意分片边、相同前缀非代表桥、热点大桶、跨桶重复对、断点重试、深链、确定性和资源保护。还需与小数据集的全对字面参考对照并量化漏检。全量运行前以试点中最长文本、实际桶偏斜、候选数及硬件余量估算；超过时间/空间预算则停止并另行调整，不把未检部分标成安全。

现有 P114 已在单一全局 SQLite 中生成跨批候选，因此完成整份输入的运行具有全局范围；以上是进一步提升效率和可恢复性的设计，尚未实现或实测。LSH 与字面方法的漏检始终存在。
